## Implemented

1. A lightweight activation state machine with four states:
   - no real knowledge yet;
   - knowledge present but no active AI connection;
   - connected-only, with no real private write yet;
   - activated after a real private create/update.
2. The connected-only state is not treated as activation.
3. The first real private write reuses existing `mcp_activity` audit records instead of creating a second analytics/audit system.
4. New OAuth writes record enough existing connection identity to resolve the exact authorization session in the admin UI.
5. The proof card presents:
   - AI / connection label;
   - create-vs-update action;
   - article title;
   - timestamp;
   - change summary;
   - human-readable changed fields;
   - a link to inspect the changed article.
6. The UI explicitly states that a successful private write does not mean the article was publicly published.
7. The no-connection next step is executable without reading the legacy MCP/Codex documentation: copy the current instance connection address, add it in the AI's connection/tool settings, complete the normal authorization page, then refresh.
8. Revoking a current connection does not erase the historical first-value proof; the UI separately shows that the connection is no longer active.

## Known risks / integration notes

1. For older OAuth activity rows created before this branch, audit attribution contains only the client id; those rows can identify the client but not the exact historical authorization session. New writes are session-specific.
2. Private-space visibility for an `update_post` is inferred using the activity status plus the post's current space membership because the existing audit schema does not snapshot `space_id`. This is sufficient for the private-beta proof path but can become historically ambiguous if a published-status article is later moved across the public/private space boundary.
3. PR #5 is intentionally draft and currently reports `mergeable: false` against a moving `main`; A4 must remain on the fixed baseline. A6 should integrate/cherry-pick from the A4 branch and resolve cross-agent overlap rather than rebasing A4 onto current main.
4. Full repository CI is still required during A6 integration because GitHub Actions did not run for this fork/API workflow.
